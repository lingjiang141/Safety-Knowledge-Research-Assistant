# Issue 10 前置：回答编排针对性架构复核

- 日期：2026-09-10｜技能：**improve-codebase-architecture**（针对性局部复核，非完整走查）
- 触发依据：`docs/development-workflow.md`「Issue 10 开始前，如回答编排已经混合检索循环、预算和格式处理
  且难以独立验证，再做针对性检查」；以及架构检查发现 ③（`answer()` 巨函数）与 ④（`revalidate` 可注入性）。
- **结论：需要在 `answer()` 之外新增一个窄接口的编排模块；不重写 `answer()` 本身。**

关键行：`answer.py:286` 直接内联了检索调用

```python
retrieval = (search or store.search)(query, 3)
```

## 2. 摩擦判断（是否"难以独立验证"）

**是。** 三个具体理由：

1. **检索已在 `answer()` 内部**，且是单次调用。加"最多两轮补充检索"意味着在 120 行函数里再嵌一层循环，
   叠加超时/错误/预算/无新证据四种停止分支——函数会从 120 行涨到 160+，进一步恶化发现 ③。
2. **停止原因需要独立断言**。PRD 4.2 要求返回"终止原因和外部执行轨迹"；若停止逻辑埋在 `answer()` 里，
   测试它必须构造完整 `store+ledger+send` 环境（正是发现 ③ 记录的摩擦点）。
3. **`revalidate` 的可注入性缺口（发现 ④）会放大**：循环中每轮都可能触发证据失效，需要能独立测该分支。

## 3. 决策：新增 `skra/orchestrate.py`（窄接口），不改 `answer()` 契约

- **编排器只做迭代与停止判定**，不生成回答：它调用**任意** `search(query, limit)` 与
  **任意** `answer_once(evidence)` 回调，因此可以注入全部假实现，无需真实模型或账本。
- `answer()` **保持不变**：仍是单次生成入口。编排器负责决定"要不要再来一轮"，`answer()` 负责"这一轮怎么答"。
- **停止原因是一等输出**：`stop_reason` 与 `trace` 由编排器组装并写入 `runs`，可离线复查。
- **不引入新检索后端**：08 的结论已表明瓶颈在切分粒度与跨资料排序，本轮不堆检索路数，只做有界迭代。

## 4. 与已有发现的衔接

- 发现 ③（巨函数）：**本轮不重构 `answer()`**，只在它外面加一层。若 10 之后 `answer()` 仍难验证，
  再按架构检查的候选解法拆 `prepare_config` / `call_model` / `assemble_output`。
- 发现 ④（`revalidate` 可注入性）：编排器的轮次回调使"轮次中途证据失效"成为可独立构造的场景，
  **顺带缓解**该缺口；不在本轮强行重构 `answer()`。
- 发现 ①（提示词版本白名单漂移）：**本任务的 trace 会记录 `prompt_version`**，为 ① 的后续收敛提供
  单点来源；本轮不改白名单机制。
