## 0. 本次修好的一个真实缺陷（先讲，因为它决定了数字是否可信）

**缺陷**：`run_baseline(..., holdout=...)` 会加载保留集，但计算时**始终只评 dev 的 `loaded.cases`**，
且把 `sample_kind` **硬编码为 `"development"`**。后果：一次"保留集最终评测"会把**dev 的分数
挂在保留集标题下**——这正是验收项①明令禁止的"先看保留集再调参、然后当独立成绩汇报"的反面。

**修法（按 tdd）**：

1. 先写失败测试 `tests/test_eval.py::FinalHoldoutEvaluationTest`（4 例，3 红）：
   - 显式 `kind="holdout"` 时必须评保留集；
   - 报告须标 `sample_kind=="holdout"` 且 `evaluated_case_ids==["H01"]`；
   - 普通运行仍须是 `development`；
   - 最终报告**不得**再声称"保留集仍封存"。
2. 最小修复：`run_baseline` 增加 `kind` 参数并推导
   `kind = kind or ("holdout" if holdout is not None else "development")`；
   校验 `kind` 合法；若 `kind=="holdout"` 却未加载保留集则报错；
   `cases = loaded.holdout if kind == "holdout" else loaded.cases`；
   报告写 `"sample_kind": kind` 与 `"evaluated_case_ids": [...]`；
   `kind=="holdout"` 时从 `not_run` 中剔除"保留集执行"一行。
3. CLI：`skra eval --holdout ...` 传 `kind="holdout"`。

25 例 eval 测试全绿。**下面的数字是修复后重跑的**，不是修复前的。

## 3. 三个真实失败案例（验收项 ④，逐例给定位与处理/未解原因）

三例的共同根因：`heading-lines-v1:20` 把**标题 + 来源 + 出版者 + 导语**压进一个 18–20 行的块，
答案被埋在其中、嵌入被稀释 → 排序挤不进前 5。**覆盖片段确实存在，是"排序未进前 5"，不是"资料没有"。**

### 案例一：H04 —— 0.00，覆盖块是整个文档头（L1–18）

- 问题：允许模型自主调用扩展时，为什么会放大提示注入的影响？
- 标注：2 个 bundle（均 `required_together`），**覆盖片段都是同一块** `2d61fd19df57`（L1–18）。
- 现象：该块**在向量 top-5 之外**（独立复现时排第 7 名），两 bundle 都未检索到 → recall 0.00。
- 定位：根因是**切分过粗**——① 号块把 5 个字段挤在一起，正是"按行等分"的已知代价。
- 处理：**未修**（不改固定检索器）；已记入 **13/14/11 结构适配**候选：
  按标题/语义块切分（`heading-block-v2` / `heading-procedure-v3` 已在演示范围内）。
- 状态：**未解决，已定位、已交接**。

### 案例二：H09 —— 0.00，覆盖块 L45–64（"预防与缓解"整节）

- 问题：限制扩展权限对减少损害有多大作用？在样例系统上能减少多少误操作？
- 标注：1 个 bundle，覆盖片段 `7e3ff71da9ec`（L45–64）。
- 现象：该块**未进前 5** → recall 0.00。
- 定位：同上，20 行块把"预防策略"整节压成一块，节内答案段被稀释。
- 处理：**未修**，与 H04 同属结构适配项。
- 状态：**未解决，已定位、已交接**。

### 案例三：H03 —— 0.50，两个标注束只取回一个（**部分取回，不是全落空**）

- 问题：资料建议用哪些措施来缓解提示注入？
- 标注：2 个 bundle（均 `required_together`）：
  - 束 B（措施4，L52–54）的覆盖块 `a0636ee4f451`（L36–55）→ **已检索到，第 3 名**；
  - 束 A（措施6，L60–62）的覆盖块 `45f7c6e76593`（L56–67）→ **未进前 5**（`retrieved_chunks` 为空）。
- 现象：**取回 1/2 个标注束 → `recall_at_5 = 0.50`**。
  这是 bundle 规则的**自觉设计**：`required_together` 的 bundle 只有**全部覆盖片段都进前 5** 才算该束命中。
- **重要区分（回答"找到一个也应返回"）**：`0.50` 不是"系统拒绝回答"。系统照常**返回它取到的那部分**
  （`status=partial`、列出措施4、明确说明缺了措施6）——**"取到部分就答部分"的行为是满足的**。
  这个数字衡量的是「**检索有没有把标注的证据取全**」，不是「系统有没有作答」。
  唯一未被认定为"通过"的，是"**只取到一半也算这道题通过**"这件事；度量层面保持保守，
  以免把 0.75 报高。**行为与度量是两条轴，不要混在一起。**
- 定位：束 A 的覆盖块 L56–67 装有**三**件事（措施5/6/7），与 §3 前两例同病——**块过粗、被稀释**。
- 处理：**未修**；bundle 规则"宁可判部分也不放宽"是**正确的保守**，不因单例下调。
- 状态：**未解决（设计如此），已定位**。

> **诚实边界**：以上三例都是**检索排序**问题，不是生成问题（生成侧本任务未运行）。
> 另有一例**已修复的真实缺陷**（§0 的 `run_baseline` 误评）也算真实失败案例，
